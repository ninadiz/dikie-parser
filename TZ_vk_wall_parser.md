# Техническое задание: Парсер стены VK-группы + админ-панель

## 1. Назначение проекта

Веб-приложение для сбора постов со стены VK-группы через официальный VK API и их просмотра в собственной админ-панели с фильтрацией по датам и базовой статистикой. Развёртывается на shared-хостинге (PHP/MySQL), без выделенного сервера.

---

## 2. Технологический стек

| Компонент | Технология |
|---|---|
| Backend | PHP (без фреймворка — обычные скрипты + простой роутинг) |
| База данных | MySQL |
| Frontend админки | React + Tailwind CSS (SPA), собирается локально/в CI через Vite в статический бандл, который заливается на хостинг как статические файлы |
| Внешний API | VK API (метод `wall.get`, при необходимости `users.get` для резолва `screen_name`) |
| Хостинг | Shared-хостинг HostiMan (PHP + MySQL + Cron доступны через ISPmanager/cPanel) |
| Версионирование / деплой | Приватный репозиторий на GitHub; на хостинге — `git clone`/`git pull` по SSH (хостинг не хранит репозитории сам) |
| Секреты | `config.php`, вне репозитория (`.gitignore`), создаётся вручную на сервере при деплое |
| Изменения схемы БД | Файлы миграций в `migrations/`, отслеживание применённых через таблицу `migrations` |
| Планировщик | Cron доступен на хостинге, но **на первом этапе не используется** — дозагрузка постов только вручную, кнопкой в админке |
| Сборка фронтенда | Node.js + Vite — используются только локально/в CI (на хостинге Node.js нет и не нужен); в репозиторий/на хостинг попадает уже собранный статический бандл (`dist/`) |

## 4. Схема базы данных

### Таблица `posts`
| Поле | Тип | Описание |
|---|---|---|
| `id` | INT AUTO_INCREMENT PK | внутренний ID |
| `vk_post_id` | BIGINT UNIQUE NOT NULL | ID поста в VK (для защиты от дублей) |
| `text` | TEXT | текст поста |
| `published_at` | DATETIME NOT NULL | дата публикации (из `date` VK, unix timestamp → DATETIME) |
| `author_id` | BIGINT | `from_id` из VK |
| `author_link` | VARCHAR(255) | `https://vk.com/id{author_id}` |
| `links` | JSON | массив ссылок, найденных в тексте поста |
| `fetched_at` | DATETIME DEFAULT CURRENT_TIMESTAMP | когда запись попала в БД |

Индекс: `INDEX (published_at)` — для быстрой фильтрации по датам.

### Таблица `settings`
| Поле | Тип | Описание |
|---|---|---|
| `key` | VARCHAR(64) PK | напр. `baseline_date` |
| `value` | VARCHAR(255) | значение |

Начальное значение: `baseline_date = 2021-05-06`.

### Таблица `migrations`
| Поле | Тип |
|---|---|
| `id` | INT AUTO_INCREMENT PK |
| `filename` | VARCHAR(255) |
| `applied_at` | DATETIME DEFAULT CURRENT_TIMESTAMP |

## 5. Интеграция с VK API

- Метод: `wall.get` (owner_id или domain группы, `count`, `offset`, `access_token`, `v`).
- Лимит VK: не более ~3 запросов в секунду → между запросами `sleep` ~0.34 сек.
- **Логика дозагрузки (инкрементальная):**
  1. Взять последний сохранённый пост и его точную дату-время публикации: `SELECT published_at, vk_post_id FROM posts ORDER BY published_at DESC, vk_post_id DESC LIMIT 1`.
  2. Запрашивать `wall.get` начиная с `offset=0` (посты идут от новых к старым), идти по страницам до текущего момента, и останавливаться **только** когда встретится пост с `published_at` **строго меньше** (не ≤) даты-времени последнего сохранённого поста, либо с равным `published_at`, но `vk_post_id` меньше либо равным сохранённому.
     - ⚠️ Важно: сравнение по одной только дате (без времени) приводит к пропуску постов — если в последний сохранённый день опубликовано несколько постов, сравнение «дата ≤ последней даты» останавливает загрузку раньше, чем нужно, и новые посты того же дня, но с более поздним временем, не попадают в базу. Поэтому `published_at` обязательно хранит дату **и** время (см. раздел 4), а сравнение идёт по полному timestamp, с `vk_post_id` как вторым критерием при полном совпадении времени.
  3. Каждый новый пост вставлять с `INSERT ... ON DUPLICATE KEY UPDATE` по `vk_post_id`, чтобы избежать дублей при повторном запуске (защитный механизм на случай гонки/повторного запуска, а не основной механизм остановки).
- **Извлечение ссылок из текста:** регулярное выражение на `https?://\S+`, сохранить как JSON-массив.
- **Автор:** `from_id` из ответа VK → `author_link = "https://vk.com/id{from_id}"`. Если нужен человекочитаемый `screen_name` — дополнительный вызов `users.get` (опционально, можно добавить позже).

## 6. Основные сценарии использования

**Сценарий 1: Первичная загрузка данных**
Администратор запускает `fetch.php` (через SSH или временную ручку) — скрипт загружает всю историю постов с даты создания группы, сохраняет в `posts`.

**Сценарий 2: Просмотр таблицы постов**
Администратор открывает `index.php`, авторизуется (логин/пароль), видит:
- нулевую дату отсчёта статистики (редактируемое поле, дефолт 06.05.2021)
- блок статистики: количество постов за выбранный диапазон, либо за весь период (от нулевой даты) если диапазон не выбран
- таблицу постов: дата, текст, ссылка на автора, ссылки из текста
- два поля выбора дат + кнопка «Применить фильтр»

**Сценарий 3: Фильтрация по датам**
Администратор выбирает `date_from`/`date_to`, таблица и блок статистики обновляются через AJAX-запрос к `api/posts.php` и `api/stats.php` без перезагрузки страницы.

**Сценарий 4: Принудительная дозагрузка**
Администратор нажимает кнопку «Догрузить новые посты» → AJAX-запрос к `fetch.php` → скрипт запрашивает у VK только посты новее последнего сохранённого → вставляет в БД → фронтенд показывает сообщение «Загружено N новых постов» и обновляет таблицу.

**Сценарий 5: Изменение нулевой даты**
Администратор меняет дату в поле наверху → `POST` к `api/settings.php` → значение сохраняется в таблице `settings` → статистика по умолчанию пересчитывается от новой даты.

**Сценарий 6: Обновление кода без потери данных**
Разработчик пушит изменения в GitHub → на хостинге по SSH выполняется `git pull` → `config.php` (вне репозитория) не затрагивается → если менялась структура БД, отдельно запускается `run_migrations.php`.

## 7. Backend: методы работы с БД

Все запросы через PDO с подготовленными выражениями (никакой конкатенации SQL-строк).

- `getPosts(?string $dateFrom, ?string $dateTo, int $limit = 150, int $offset = 0): array` — `SELECT * FROM posts WHERE (:dateFrom IS NULL OR published_at >= :dateFrom) AND (:dateTo IS NULL OR published_at <= :dateTo) ORDER BY published_at DESC, id DESC LIMIT :limit OFFSET :offset`; при росте объёма данных заменить на курсорный вариант (`WHERE (published_at, id) < (:lastPublishedAt, :lastId)`)
- `getPostsCount(?string $dateFrom, ?string $dateTo): int` — то же самое, но `COUNT(*)`; если оба параметра `null`, диапазон — от `baseline_date` до текущей даты
- `upsertPost(array $post): void` — `INSERT ... ON DUPLICATE KEY UPDATE` по `vk_post_id`
- `getLastPost(): ?array` — `SELECT published_at, vk_post_id FROM posts ORDER BY published_at DESC, vk_post_id DESC LIMIT 1`; возвращает точную дату-время и ID последнего поста для корректной остановки дозагрузки (см. раздел 5)
- `getSetting(string $key): ?string` / `setSetting(string $key, string $value): void` — работа с таблицей `settings`

## 8. Frontend: вывод постов в таблицу (React + Tailwind)

- SPA на React (собран через Vite), стилизация — Tailwind CSS.
- `App.jsx` при монтировании делает `fetch('/api/posts.php')` и `fetch('/api/stats.php')` (без параметров дат — возвращается полный период от `baseline_date`), сохраняет в state.
- **Пагинация — бесконечный скролл с буферизацией:**
  - `api/posts.php` принимает `limit` и `offset` (либо курсор — см. ниже), сортировка строго `ORDER BY published_at DESC, id DESC` (детерминированный порядок, без «дребезга» при одинаковых датах).
  - Один запрос сразу тянет 150 постов (`limit=150`): 50 рендерятся в таблицу, 100 остаются в React-state как буфер, не попадая в DOM.
  - При скролле, когда показанные 50 подходят к концу, следующие 50 берутся из буфера мгновенно (без сети) — именно это даёт быстрый скролл.
  - Когда буфер опускается ниже ~50 записей, в фоне запускается подгрузка следующей порции (следующие 100) — незаметно для пользователя, пока он читает уже показанное.
  - При смене диапазона дат (`DateRangeFilter`) буфер и текущий offset/курсор сбрасываются в 0, запрос идёт заново.
  - При большом объёме постов (тысячи+) offset-пагинация в MySQL деградирует на глубоких страницах — в этом случае переходить на курсорную пагинацию: `WHERE (published_at, id) < (:last_published_at, :last_id) ORDER BY published_at DESC, id DESC LIMIT :limit`.
  - Если список вырастет до многих сотен показанных строк одновременно, для сохранения плавности скролла можно добавить виртуализацию (`react-window`) — рендерит только видимые в вьюпорте строки; не обязательно для первой версии.
- Компоненты:
  - `BaselineDateInput` — поле нулевой даты, при изменении делает `POST /api/settings.php`
  - `StatsBar` — отображает счётчик постов, обновляется при смене фильтра
  - `DateRangeFilter` — два поля дат + кнопка «Применить» → сбрасывает пагинацию, триггерит повторный `fetch('/api/posts.php?date_from=...&date_to=...&limit=150&offset=0')` и `fetch('/api/stats.php?...')`
  - `PostsTable` — таблица (Tailwind-классы для сетки/зебры), колонки: дата, текст, автор-ссылка (`<a>` на `author_link`), ссылки из текста (список `<a>`); подписана на скролл-контейнер для триггера показа из буфера/подгрузки
  - `FetchNewPostsButton` — `POST /fetch.php`, показывает состояние загрузки (спиннер/disabled), после ответа обновляет список постов и статистику
- Все запросы к PHP-эндпоинтам идут с `credentials: 'include'`, чтобы передавалась сессионная cookie (авторизация через PHP-сессии, не JWT).
- Формат ответа `api/posts.php` — `{items: [{id, published_at, text, author_link, links}, ...], hasMore: boolean}`.
- Ссылки из текста рендерятся в таблице как список `<a>`-тегов, а не как plain text.
- CORS не требуется, если React-бандл раздаётся с того же домена, что и PHP API (рекомендуемая схема — единый домен, `dist/` в корне или в `/admin/`, API — в `/api/`).

## 9. Аутентификация

- Одна пара логин/пароль (хранится в `config.php` как хэш, либо в таблице `users` — на выбор при реализации).
- `LoginForm.jsx` (React) отправляет `POST /login.php` с `credentials: 'include'` → PHP проверяет пароль → `$_SESSION['authenticated'] = true`, отдаёт cookie сессии.
- Все `api/*.php` и `fetch.php` в начале проверяют `$_SESSION['authenticated']`, иначе отдают `401` — React-приложение при получении 401 показывает форму логина.
- `logout.php` — `session_destroy()`, вызывается из React по кнопке «Выйти».
